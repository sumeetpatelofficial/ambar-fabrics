# Implementation Roadmap

Execution rule: one phase at a time. Each phase ends with the format, lint, typecheck, tests, and build results (actual output), an updated `docs/project-status.md`, and a stop for approval.

## 1. Dependency map

```
0 Blueprint ─► 1 Foundation ─► 2 Design system/shell ─► 3 Catalog data ─► 4 Storefront pages
                     │                                        │                  │
                     └──► 5 Auth/accounts ───────────────────┼──► 6 Cart+inventory ─► 7 Checkout+Razorpay ─► 8 Shipping/fulfilment
                                                              │                                   │
                                  9 Admin (grows from 3; the admin shell and RBAC start at 5) ◄───┘
                                  10 SEO/content ◄ 4,9     11 Analytics ◄ 4,7     12 Emails/CX ◄ 7,8
                                  13 Security/perf/QA ◄ all         14 Deploy/launch ◄ 13
```

Notes on ordering:

- Phase 5 (auth) must precede Phase 7 (checkout needs a logged-in user, A-4).
- The admin RBAC skeleton, `assertPermission`, and `AuditLog` are built in Phase 5, so every later phase can add admin screens as it goes. Phase 9 then completes the remaining admin modules, so admin work is not left for the end.
- Email infrastructure (the `Job` outbox, the console/Resend adapters) arrives in Phase 5 for verification emails. Phase 12 adds the full template set.

## 3. Per-phase working protocol

1. State scope, dependencies, files to create/modify, and acceptance criteria.
2. Read the relevant files and verify library APIs against installed versions (no remembered APIs for Next 16, Auth.js 5 beta, Mongoose 9, Motion 14).
3. Implement, write tests, and run format, lint, typecheck, tests, and build.
4. Update docs and `project-status.md`.
5. Report: what was built, files changed, **actual** test results, limitations, how to verify, recommended next phase. Then stop.

Anything that cannot be verified because an external credential or service is missing is reported as "not verified", with the exact blocker.

## 5. Owner answers (2026-10-13) and their effect

1. **GST:** not registered yet, will register later. → `SiteSettings.tax.enabled` defaults to **false**. While it is off, no GST is calculated or shown, and invoices are plain invoices or bills of supply without a tax breakup. Per-product HSN and rate fields exist and stay dormant. Turning tax on later changes only settings, with no code or schema change. Orders already placed keep their stored snapshot. Which invoice type is legally right before registration is for your accountant to confirm.
2. **Returns:** returns are allowed for ready-made items. The message was cut off after "but for cut fabrics"; I'm treating it as **cut fabrics are not returnable** (A-9) until you correct me. Unstitched 3-piece material is sold as a fixed set, so its returnability needs your decision (default: returnable only if unopened or faulty, configurable per product).
3. **Razorpay and Shiprocket:** no accounts yet. Credentials will be supplied through env vars. → Development uses Razorpay test keys when you create a test account (free, no KYC) and the mock shipping adapter. Live mode needs KYC, which has to happen before Phase 14. It is a business step on your side and can run in parallel.
4. **Domain:** purchased. → Used for `NEXT_PUBLIC_APP_URL`, OAuth callbacks, email sending domain, and Search Console in Phase 14. The brand name is still a settings value until you confirm it.
5. **Catalogue:** about 200 products across fabrics (cotton, crepe, modal silk, chinon, tissue), dupattas (with subcategories), blouses, ready-made dresses/kurtis, and unstitched 3-piece material. → The MongoDB text index and filters are enough (A-13 confirmed). Atlas Search and heavy CSV tooling are low priority. Categories should be a two-level tree (for example Fabrics → Cotton), which the schema already supports. Fabric type becomes a filterable attribute (cotton, crepe, modal silk, chinon, tissue).
